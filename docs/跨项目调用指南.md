# 跨项目调用 QuantBacktest 指南

本文面向在**其他本地项目目录**中研究、挖掘或复现加密货币因子的研究员。它说明如何准备符合 QuantBacktest 规范的 Python 因子脚本和 YAML 配置，并通过 Web、CLI 或 Python API 执行回测。

新论文因子建议从 `factor_research` 开始：它检验因子对指定资产池未来横截面收益的预测能力，不把分组收益解释为一个带杠杆的交易账户。只有需要单独评估可交易性时，才选择 `strategy_simulation`。

## 1. 推荐的外部项目结构

下面的结构只是建议；目录名称可以改变。关键规则是：YAML 中的相对路径以**源项目目录**为基准解析，运行结果自动写入 `<源项目目录>/results/backtests`。

```text
my-factor-project/
├── factors/
│   └── momentum_factor.py
├── configs/
│   ├── factor_research.yaml
│   ├── strategy_simulation.yaml
│   └── ml_factor_research.yaml
├── data/
│   └── raw/
│       └── crypto_top50/
└── results/
    └── backtests/              # QuantBacktest 自动创建并写入
```

数据目录不需要复制到 QuantBacktest 核心项目中。请在 YAML 中声明数据适配器、市场、频率、资产和时间范围；相对的 `data.path`（如 `data/raw/crypto_top50`）由调用方项目解析。

运行前请确保核心工具已经安装在专用环境中，并在外部项目根目录执行命令：

```powershell
conda activate backtest-system
cd E:\research\my-factor-project
quantbacktest validate configs\factor_research.yaml
quantbacktest inspect-factor factors\momentum_factor.py
quantbacktest run configs\factor_research.yaml
```

`validate` 只检查 `RunSpec`、数据覆盖和策略约束；`inspect-factor` 只读取因子脚本声明；`run` 才会执行受信任的本地 Python 因子脚本并写入运行结果。

## 2. 三种调用方式

### Web：导入外部项目回测

1. 在 Streamlit 的“外部项目导入回测”区域填写**源项目绝对目录**，例如 `E:\research\my-factor-project`。
2. 上传一个 `.py` 因子脚本和一个 `.yaml` 或 `.yml` 配置文件。
3. 检查界面显示的解析后数据路径、因子快照 SHA-256、标准化配置和输出目录。
4. 如有需要，用 UTC 起止日期控件覆盖 YAML 的日期；覆盖后的标准化 `RunSpec` 会随运行保存。
5. 阅读“上传脚本将被执行”的提示，确认脚本可信后运行。

上传不会改写外部项目中的原始脚本或 YAML。脚本会作为本次运行的不可变快照缓存，YAML 内的 `factor.module_path` 会自动指向该快照；输出根目录固定为 `<源项目目录>/results/backtests`。

### CLI：先验证、再运行

请从源项目根目录运行，以使所有相对路径保持可复现：

```powershell
quantbacktest validate configs\factor_research.yaml
quantbacktest inspect-factor factors\momentum_factor.py
quantbacktest run configs\factor_research.yaml
```

如果配置中使用绝对路径，也仍建议在源项目根目录运行，这样生成的相对记录、因子快照和结果目录更容易追踪。

### Python API：最小调用示例

```python
from pathlib import Path

import yaml

from quantbacktest.engine import run_backtest
from quantbacktest.schemas import RunSpec

project_root = Path(r"E:\research\my-factor-project")
config_path = project_root / "configs" / "factor_research.yaml"
payload = yaml.safe_load(config_path.read_text(encoding="utf-8"))
spec = RunSpec.model_validate(payload)

result = run_backtest(spec, project_root)
print(result.run_dir)
```

第二个参数必须传入源项目根目录，才能使 `data.path` 和 `factor.module_path` 的相对路径按预期解析。

## 3. Python 因子脚本契约

因子脚本必须定义字典 `FactorMeta` 和函数 `compute_factor(context)`。其中 `FactorMeta` 至少包含：

| 字段 | 含义 |
| --- | --- |
| `required_fields` | 因子需要的数据字段，例如 `timestamp`、`symbol`、`close`。运行前会校验。 |
| `min_lookback_bars` | 计算一个有效因子值最少需要的历史 K 线根数。 |
| `supported_modes` | 支持的策略模式列表：横截面因子使用 `cross_sectional`；单资产策略使用 `single_asset`。 |

可选的 `output_columns` 可声明输出列，例如 `['factor']`。`context.data` 是系统已经标准化后的 OHLCV 面板；`context.parameters` 是 YAML 中 `factor.parameters` 的字典。

输出必须是 `pandas.DataFrame` 或可转换为 DataFrame 的对象，并且至少含有：

```text
timestamp, symbol, factor
```

- `timestamp` 必须表示 UTC 时点；系统会统一转为 UTC。
- 每个 `(timestamp, symbol)` 至多一行；系统会去重并按 `timestamp, symbol` 排序，但脚本自身也应避免产生重复。
- 初始窗口产生的 `NaN` 是正常的；不要用未来值补齐缺失，也不要删除原始时间信息。
- `compute_factor` 在形成时点只能使用该时点及以前的数据。禁止 `shift(-1)`、未来收益、未来滚动窗口、后向填充或任何依赖未来 K 线的处理。
- 不要在脚本中计算并返回未来收益标签；标签由研究评估层按 YAML 的研究收益口径统一生成。

下面是可直接复制的截面动量因子。它使用每个币种过去 `lookback_bars` 根 K 线的收益率作为原始分数。

<!-- snippet:factor_python -->
```python
from __future__ import annotations

import pandas as pd


FactorMeta = {
    "required_fields": ["timestamp", "symbol", "close"],
    "min_lookback_bars": 24,
    "supported_modes": ["cross_sectional"],
    "output_columns": ["factor"],
}


def compute_factor(context) -> pd.DataFrame:
    lookback_bars = int(context.parameters.get("lookback_bars", 24))
    data = context.data[["timestamp", "symbol", "close"]].copy()
    data["factor"] = data.groupby("symbol", group_keys=False)["close"].pct_change(
        lookback_bars
    )
    return data[["timestamp", "symbol", "factor"]]
```

## 4. 合格 YAML 样例

三个样例都假设使用上一节的 `factors/momentum_factor.py`。请将币种、数据适配器、路径、时间范围和论文信息替换为自己的研究对象。`symbols` 至少给出 10 个可用资产，才能进行横截面研究或横截面策略。

### 4.1 论文因子研究：`factor_research`（默认模板）

此模式必须显式写明因子形成时表、预测收益口径、方向和分组规则。以下配置每日 UTC `00:00` 形成因子，以形成时的收盘价到下一日同一时刻收盘价定义未来收益；高分预测高收益。

<!-- snippet:factor_research_yaml -->
```yaml
name: external_momentum_research
data:
  adapter: crypto_top50
  path: data/raw/crypto_top50
  market: spot
  frequency: 1h
  symbols: [BTCUSDT, ETHUSDT, BNBUSDT, SOLUSDT, XRPUSDT, ADAUSDT, DOGEUSDT, LTCUSDT, LINKUSDT, AVAXUSDT]
  start: 2024-01-01T00:00:00Z
  end: 2024-06-30T23:00:00Z
  universe:
    min_assets: 10
    min_history_bars: 24
factor:
  module_path: factors/momentum_factor.py
  callable: compute_factor
  parameters:
    lookback_bars: 24
evaluation:
  mode: factor_research
  research:
    formation:
      kind: calendar
      interval: 1d
      time_utc: "00:00"
    returns:
      horizon: 1d
      start_price: close
      end_price: close
    direction: higher_predicts_higher_return
    portfolio:
      selection: quantiles
      quantiles: 3
      weighting: equal
    ic_decay_horizons: [1h, 4h, 1d]
debug:
  mode: trace
output:
  root: results/backtests
provenance:
  paper_title: External momentum research
  paper_reference: https://example.com/paper
  notes: Replace this placeholder with the paper's formation and return conventions.
  proxy_data_note: Declare any data-source or frequency proxy here; leave empty only when none is used.
```

研究报告会输出原始未来分组收益、按方向修正的 Top−Bottom、Rank IC、ICIR、IC 衰减、覆盖率、换手、集中度、单币贡献与逐币剔除诊断。Top−Bottom 在此是统计差值，不是账户净值，因此不会生成 CAGR、爆仓或保证金结论。

自然日历形成不会按“可用 bar 的数量”漂移。如果要求的 UTC 锚点 K 线缺失，系统会跳过该期并在结果中记录原因；不会悄悄向前或向后移动形成时点。

### 4.2 策略模拟：`strategy_simulation`

此模式评估明确的持仓、调仓和成本假设。下面的例子选取最高两只和最低两只动量币，构造美元市场中性组合，每 24 根 1 小时 K 线调仓并持有 24 根 K 线。回撤止损是组合账户规则，不应作为论文因子预测力的结论。

<!-- snippet:strategy_simulation_yaml -->
```yaml
name: external_momentum_strategy_simulation
data:
  adapter: crypto_top50
  path: data/raw/crypto_top50
  market: spot
  frequency: 1h
  symbols: [BTCUSDT, ETHUSDT, BNBUSDT, SOLUSDT, XRPUSDT, ADAUSDT, DOGEUSDT, LTCUSDT, LINKUSDT, AVAXUSDT]
  start: 2024-01-01T00:00:00Z
  end: 2024-06-30T23:00:00Z
  universe:
    min_assets: 10
    min_history_bars: 24
factor:
  module_path: factors/momentum_factor.py
  callable: compute_factor
  parameters:
    lookback_bars: 24
evaluation:
  mode: strategy_simulation
strategy:
  mode: cross_sectional
  selection: top_k
  top_k: 2
  long_short: market_neutral
  weighting: equal
  rebalance_bars: 24
  execution:
    signal_price: close
    entry_price: next_open
    holding_bars: 24
  risk_control:
    max_drawdown_stop:
      enabled: true
      threshold: 0.15
costs:
  fee_bps: 5.0
  slippage_bps: 5.0
debug:
  mode: trace
output:
  root: results/backtests
provenance:
  paper_title: External momentum strategy simulation
  paper_reference: https://example.com/paper
  notes: This is an explicit tradability simulation, not the paper factor conclusion.
  proxy_data_note: Spot prices synthesize short-side returns; borrowing, funding and margin constraints are not included.
```

系统在当前 K 线收盘生成信号，默认在下一根 K 线开盘成交。启用止损时，成本后收盘净值相对历史峰值的回撤达到阈值后，下一根 K 线开盘统一平仓；清仓后持有现金，直到下一个既定调仓时点才允许再入场。对现货价格构造的空头，报告会标记为合成收益模拟，而不是可直接执行的永续账户。

### 4.3 ML 融合评分：LightGBM 研究模板

当前首版 ML 层使用基础因子脚本输出的原始 `factor` 分数和未来收益标签进行时间切分训练，并只对时间外样本评分。它不把任意多个 DataFrame 列自动当作特征；多特征融合应在经审核的因子脚本中先形成一个基础分数，或在后续扩展中使用专门的特征接口。

至少需要 20 个有效形成时间截面。系统会保存特征顺序、模型参数、随机种子、依赖版本、模型哈希和模型工件。下面是最小 LightGBM 配置：

<!-- snippet:ml_factor_research_yaml -->
```yaml

  start: 2024-01-01T00:00:00Z
  end: 2024-06-30T23:00:00Z
  universe:
    min_assets: 10
    min_history_bars: 24
factor:
  module_path: factors/momentum_factor.py
  callable: compute_factor
  parameters:
    lookback_bars: 24
evaluation:
  mode: factor_research
  research:
    formation:
      kind: calendar
      interval: 1d
      time_utc: "00:00"
    returns:
      horizon: 1d
      start_price: close
      end_price: close

    portfolio:

  enabled: true
  model: lightgbm

    n_estimators: 100
    random_state: 42

debug:

output:
  root: results/backtests
provenance:

  notes: LightGBM is trained and evaluated with a time-based out-of-sample split.
  proxy_data_note: Declare any proxy-data limitation here.
```

## 5. 数据、时间与可复现性检查

1. 系统唯一时区是 UTC。配置中的时间应使用带 `Z` 的 ISO 8601 时刻，例如 `2024-01-01T00:00:00Z`。
2. 原始数据适配层会统一排序、去重并记录数据指纹；但数据字段映射、来源、覆盖区间和代理数据说明仍必须在配置或数据登记中准确声明。
3. `factor_research` 中的 `formation`、`returns`、`direction` 和 `portfolio` 是条件必填项。每篇论文都必须明确这些复现假设，系统不会默认日频、周频或 672 根 bar。
4. 静态 `symbols` 可以使用，但报告会展示实际可用币数、缺失率和集中度。若论文需要上市、下市或可交易资格变化，请提供时间点资产池清单，而不是用今天的静态名单代替历史资产池。
5. 若使用代理数据，请填写 `provenance.proxy_data_note`，清楚说明数据来源、频率映射和预期偏差；未声明的代理数据不应被视为论文严格复现。

## 6. 常见配置错误与修复

| 报错或现象 | 原因 | 修复方式 |
| --- | --- | --- |
| `FactorMeta` 缺失或字段不足 | 脚本没有声明所需字段、最小历史长度或支持模式 | 增加 `required_fields`、`min_lookback_bars`、`supported_modes`。 |
| 因子输出缺少 `timestamp`、`symbol` 或 `factor` | `compute_factor` 返回了中间表或列名不符合契约 | 明确返回这三列，且每个时点和币种只保留一个分数。 |
| 研究模式校验失败 | 未提供 `evaluation.research`、方向、收益口径或分组规则 | 复制 4.1 的完整 `research` 块，再按论文修改。 |
| 横截面资产不足 | 某期有效币数少于 `universe.min_assets` 或横截面策略要求 | 扩充合格资产池、调整研究区间，或如实降低最小资产数（不要把单资产当作横截面结论）。 |
| 数据路径不存在或覆盖不足 | 相对路径不是以源项目目录解析，或请求日期超出数据范围 | 从源项目根目录运行 CLI；检查 `data.path`、`start`、`end` 和适配器登记。 |
| 因子脚本在导入后找不到数据 | 脚本试图自行读取相对文件，而不是使用 `context.data` | 把数据读取交给 `data` 配置；脚本只基于 `context.data` 计算因子。 |
| 结果与论文不一致 | 资产池、价格口径、形成日历或代理数据与论文不同 | 在 `provenance` 中记录偏差，逐项对齐论文的形成、收益和筛选规则，再使用 trace/replay 定位。 |
| ML 样本不足或泄漏被拒绝 | 有效形成截面少于 20，或训练标签跨越测试开始时点 | 延长样本、降低不必要的跳过期，并保持严格时间外训练/验证/测试。 |

遇到复杂论文复现时，优先使用 `debug.mode: dry_run` 检查数据覆盖和配置，再使用 `trace` 查看数据、因子、信号和研究阶段摘要；只在缩小的 UTC 窗口和指定币种上使用 `replay` 复放问题区间。

## 7. 从回测结果导入因子库

因子库流程分为候选与人工批准两个阶段：

1. 在 Web “因子库”中，可以从一条已完成回测创建候选，或直接上传 Python 脚本与 YAML 创建候选。
2. 直接上传只保存不可变快照，**不会执行脚本，也不会直接成为正式因子**。
3. 批准候选时，必须选择一条成功完成的证据运行；该运行的 `factor_snapshot.py` SHA-256 必须与候选脚本 SHA-256 完全一致。
4. 哈希匹配且研究员勾选人工确认后，候选才会成为 `approved` 正式因子。库中会保存匹配的配置、指标、报告和回测证据。

因此，请先完成并审阅可复现回测，再导入或批准因子；外部项目本身不会被因子库流程改写。
